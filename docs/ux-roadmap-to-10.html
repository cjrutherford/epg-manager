01 · The thesis

The last mile is evidence, not decoration.

The product has already crossed the hard structural line: Watch and Admin now share a system, mobile works, failures are visible, and the build is guarded by 59 end-to-end tests. What remains is to close the known exceptions, prove the result with users, and make quality repeatable.

The shortest path to a 9 is not another visual pass. It is three things: finish the one remaining information-architecture split, split the Watch stylesheet and remove the last duplicate patterns, and put accessibility and usability on a measured footing. A 10 then requires the product to keep those qualities while adding the things users remember: a guided first run, a fast and remote-friendly TV experience, designed failure states, and a design system that cannot quietly drift.

The rule for this roadmap

No phase starts before the previous gate is met. A feature that cannot be explained, tested, and measured does not enter the plan. The brand, navigation model and component vocabulary are frozen unless a gate explicitly reopens them.

02 · What 9 and 10 mean

Two different finish lines

9.0

Exceptional and proven

No known material friction. Every screen, state and device has been reviewed. Accessibility and usability are measured, not assumed.

  • Zero open P1/P2 findings
  • axe-core serious/critical: 0
  • Lighthouse accessibility: ≥95
  • SUS ≥80 · task success ≥85%
  • WCAG AA on every supported theme
  • 320px–4K, browser and Android shell
  • Watch CSS within budget
  • First sync under 2 minutes
10.0

Reference quality, sustained

A product other self-hosted tools are compared to. It anticipates failures, feels authored on every device, and has the process to stay that way.

  • Everything in 9, held for two clean releases
  • SUS ≥85 · task success ≥95%
  • WCAG AA fully; AAA where feasible
  • Screen-reader and remote-first parity
  • 60fps guide at 1,000+ channels
  • Guided first run to first channel
  • Localized and RTL-ready
  • Design system enforced by CI
  • Public quality dashboard
  • Continuous user research

A 10 is a judgement about category leadership, not a mathematical certainty. These criteria make the judgement explicit and auditable.

05 · Phases & gates

Four phases, four hard gates

Assumes one senior front-end engineer, a half-time product designer, QA/accessibility support, and a backend engineer available for failure-state and performance work. Every gate is evidence-based and must be signed off before the next phase begins.

Phase 1 — Finish the known gap

Weeks 1–3 · 7.7 → 8.4
Close every issue the post-implementation review already names.
  • IA: extract PlaylistConfigComponent; render it from Sources; finish Settings rail and sticky save; assign one owner per setting.
  • Watch debt: split the stylesheet into player, guide, recordings and overlays; meet the 32 kB budget.
  • Tokens: collapse --font-2xs/--font-xs; curate themes to five or fewer; remove duplicate component variants.
  • System proof: component contract page, visual regression baseline for all supported themes, axe-core and Lighthouse CI.
  • Craft: mobile guide scroll affordance; Settings density; remaining hover/focus/motion exceptions.
Gate 1 · Release candidateNo open P1/P2. Watch CSS ≤32 kB and total CSS down 20%. Zero duplicate patterns. axe serious/critical 0. Lighthouse accessibility ≥95. No overflow at 320/390/768/1024/1440. All supported themes pass contrast.

Phase 1 status · 5 Nov 2026

Met: playlist ownership moved to Sources; Settings rail and sticky save; Watch CSS split into four scoped files, each under the 32 kB budget; five themes; --font-2xs collapsed; mobile guide fade and swipe hint; component contracts page; axe serious/critical 0; Lighthouse accessibility 100; no page overflow at 320/390/768/1024/1440; all five themes pass the WCAG AA contrast test.

CSS gate: initial CSS across the eight public and admin routes fell from 480,864 to 363,303 bytes — 24.4% down, against the 20% target. Exact duplicate rules are at zero. The font pipeline now ships three variable families (six faces) from a cacheable stylesheet instead of 30 static faces inlined into every prerendered page, and Sources/Diagnostics share one table contract. Visual baselines cover all five themes on the login screen plus Settings (`npm run test:visual`, opt-in project).

Source trend (informational): the raw/minified source is 156.5 kB / 110.6 kB, 8.4% and 11.2% down rather than 20%. The remaining reduction needs a broader design-system rewrite, not dead-code removal.

Phase 2 — Prove it

Weeks 3–6 · 8.4 → 9.0
Replace internal confidence with user evidence.
  • Usability: five–eight first-time users; tasks: add a source, find why a channel has no guide, schedule a recording, recover from a failed stream.
  • Accessibility: screen-reader pass on guide and player; keyboard-only and D-pad runs; large-text and high-contrast sessions.
  • Cross-device: Chrome, Safari, Firefox; Android shell; 320, 390, 768, 1024, 1440 and TV.
  • Failure states: every taxonomy path tested against a purpose-built fixture, not production guesses.
  • Measurement: publish a UX scorecard: SUS, task success, time on task, error recovery, a11y and performance.
Gate 2 · 9.0SUS ≥80 and task success ≥85% with no moderator rescue. Screen-reader and D-pad paths complete. Zero serious axe issues. Lighthouse ≥95. No P1/P2. First sync under 2 minutes on clean install.

Phase 3 — Elevate

Weeks 6–12 · 9.0 → 9.5
Add the things users remember, without breaking the measured floor.
  • First run: guided source → preview → sync → first channel, with a real “watch something” moment.
  • TV/remote: full spatial focus, D-pad shortcuts, 10-foot typography, safe areas, cast/PiP, remote help.
  • Signature interactions: channel switch, guide focus, lower third, theme preview — each with a 150–250 ms motion spec.
  • Reliability: degradation warnings, stale guide notices, rate-limit explanations and offline behavior.
  • Content: editorial copy, contextual help, localized strings and RTL layout for the core flows.
  • Performance: 60fps guide at 1,000+ channels; theme switch under 150 ms; memory and INP budgets in CI.
Gate 3 · 9.5Guided first run reaches a live channel without help. Remote-only test passes. 60fps guide at 1,000+ channels. Core flows localized and RTL-safe. Two consecutive releases with no P1/P2 regression.

Phase 4 — Sustain and lead

Weeks 12–16+ · 9.5 → 10
Make excellence institutional rather than heroic.
  • Design ops: contribution guide, component versioning, deprecation policy, design review cadence.
  • Research: standing five-user panel, quarterly benchmark, findings triaged into the roadmap.
  • Quality dashboard: public or internal view of SUS, task success, a11y, performance, error recovery and open findings.
  • Release discipline: every release runs the full UX gate; visual regression on all supported themes; no silent scope creep.
  • Category leadership: publish the design system and accessibility notes; test against two comparable self-hosted tools; close any credible gap they expose.
Gate 4 · 10All 9.5 criteria hold for two clean releases. SUS ≥85 and task success ≥95%. Zero serious/critical axe issues and a completed manual SR audit. Localized and RTL core flows. Design system adoption enforced in CI. Quality dashboard live. No regression across two consecutive releases.

08 · Operating model

How the team works to keep the score

Core team

  • Senior front-end engineer — implementation, component system, performance.
  • Product designer (0.5) — interaction design, content, usability scripts.
  • QA / accessibility (0.25–0.5) — device matrix, screen reader, release gate.
  • Backend engineer (0.25) — failure taxonomy, performance, telemetry.
  • Research participants — five to eight per round, recruited from self-hosters.

Cadence

  • Weekly design review: one screen, one state, one decision.
  • Biweekly UX gate: run the full guardrail suite and visual diff.
  • Monthly scorecard: SUS, tasks, a11y, performance, open findings.
  • Quarterly research round and theme/component deprecation review.

Definition of done, per ticket

Desktop and mobile states, empty/loading/error paths, keyboard and screen-reader labels, token-only styling, a visual regression snapshot for every supported theme, and one sentence explaining the user problem it solves.

09 · Risks

What could keep us at 8

“10” turns into scope

Mitigation: the backlog is capped at the twenty tickets above. New ideas go to a parking lot and need a gate-level justification.

Visual polish hides structural debt

Mitigation: Phase 1 closes the CSS and IA debt before any signature work. No new theme or component until Gate 1.

Testing on a single machine

Mitigation: browser/Android/TV matrix in Phase 2; isolated fixture per worker; a real 10-foot test in Phase 3.

Accessibility treated as a checklist

Mitigation: automated axe, manual screen-reader script, and a D-pad-only pass. A green CI is necessary, not sufficient.

Research findings arrive too late

Mitigation: usability runs at the end of Phase 1, before signature work. Findings can reshape Phase 3, not invalidate it.

Quality drifts after the roadmap

Mitigation: visual regression, UX release checklist, scorecard review and a named design-system owner.

What we will not do

No rebrand. No more themes. No native rewrite. No new feature work during Phase 1. No “10” claim without a second release proving it.
